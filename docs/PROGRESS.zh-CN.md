## 里程碑 1：骨架与最小闭环 —— 已验收（2026-10-31）

已交付：

- SQLite 存储和带版本号的迁移；文档保存原始下载和清洗后的正文；题目、标签、切块、FTS5 索引和向量全部持久化；
  向量快照带启动时一致性检查（只补新增部分；丢失时从数据库重建；从不重新计算向量）。
- 可配置的 agent：后端（OpenAI 兼容接口、CLI agent）和带备用链的角色，分层配置和环境变量覆盖，能力校验，
  `sde-rag agents show`、`sde-rag doctor`。
- 模型调用的卡死侦测：流式输出的首个 token 超时和间隔超时，结构化调用的硬性超时，输出重复循环检测，卡死后的健康探测和熔断。
- 身份与权限接口（默认：单用户、全部可见），检索链路全程经过它，并用限制性的策略做了测试。
- 连接器：GitHub 题库仓库（41 个）、Hacker News（Algolia API）、dev.to（公开 API），支持增量列表、“已见过”记录、
  条件请求、内容哈希和跨来源链接识别。
- Markdown 规则问答抽取（标题题目、编号列表里的标题、`<details>` 折叠块、题目列表），基于可配置分类体系的规则打标签和 LLM 打标签，
  完全相同的题目合并，并计算出现次数和热度。
- 混合检索（BM25 + 向量，RRF 融合）；查询图支持列出某方向的常见题和带引用的回答，校验引用，模型失败时给出降级回答。
- 抓取图：运行标识、数据库锁（持有者进程不存在时可接管）、心跳、断点续跑。
- 最小的评测图（检索自检）、带 `/health` 的 Gradio 网页界面、命令行。
- 公开数据集导出（`sde-rag publish-data`），不含本机使用数据：原始文件用 Git LFS，数据库作为 GitHub release 附件
  （只保留最新几个），`sde-rag import-data` 下载并校验。
- 测试：不需要网络的单元测试；在 `langgraph dev` 里运行查询图的集成测试。

第一次真实抓取（2026-10-31）：486 篇文档（GitHub 文件 314 个、dev.to 文章 150 篇、Hacker News 讨论 23 个），
6,535 道不同的题，7,585 个切块，用 `intfloat/multilingual-e5-large` 计算向量。

验收（2026-10-31），对照 DESIGN.zh-CN.md 第 12 节的标准：

验收中修复的问题：

- 题目列表里编造的条目：如果一行列表只引用了上下文之外的标签，现在整行删除，而不只是去掉标签；
  命令行在校验后的回答和流式输出不一致时，会打印校验后的版本。
- 方向题目排序：请求里的泛化词（“常见”“面试题”“common”“interview questions”）不再去匹配
  “... Interview Questions”这类标题；新增“专注度”排序，优先选专门讲这个标签的来源；热度相同的题在融合时排名相同。
- 规则标签：多种语言共有的概念（“decorator”“generator”“closure”“hooks”“coroutines”）不再作为某一种语言的别名；
  分类体系版本变化时，规则标签会重新生成。
- 解析：“— Difficulty: Easy”存为难度，不再算作题目的一部分；第一人称的博客标题（“What I took away”）不算题目。
  旧版解析器处理过的文档会从已保存的正文重新解析（不重新下载），没有变化的文档切块保留原来的向量。
- 路由：如果消息本身就是一道具体的题，即使路由模型把它标成“方向”，也会直接作答。

验收后：532 篇文档（已索引 521 篇），6,633 道不同的题，8,028 个已计算向量的切块；1,200 道题由 LLM 打了标签。

已知限制（计划在后续里程碑解决）：

- 在合并近似重复之前，“常见”只能按完全相同的重复来统计：题库里“什么是生成器”有八种问法，每种只算一次，
  所以方向题目列表主要依靠来源专注度和文档内顺序。

- 只有规范化后文本完全相同的题才会合并（近似重复：里程碑 2）。
- 面经帖子以正文切块的形式入库；只有写成标题的题目会被抽出来（LLM 抽题：里程碑 2）。
- LLM 打标签每次运行处理 600 道题，其余的先保留规则标签，按顺序轮到。
- 评测图目前只检查索引能否用题目原文找回这道题（真正的评测集：里程碑 3）。

### 第 1 步：可靠性和定时任务 —— 已完成（2026-10-31）

- 死信：`sde-rag replay --list` 列出，`sde-rag replay [--stage] [--status dead|failed] [--ids]` 让文档在下一次运行时
  重新经过对应阶段（尝试次数清零）。建索引阶段现在也按文档记录失败，一篇文档出错不再中断整个阶段。
- 来源退避：连续失败的来源依次等 1、2、4 个抓取间隔再试，最多 48 小时（以前每次运行都会重试）。
- 运行看门狗：抓取进程里的线程检查进展（每处理完一条记录、每列出一个条目都算进展）；20 分钟没有任何进展时，
  把所有线程的调用栈写到 `data/logs/stall-*.txt`，把运行标记为 `stalled`，释放锁，告警，然后以退出码 3 退出。
  启动新运行时，仍标记为 `running` 但进程已经不在的运行改记为 `abandoned`。
- 模型卡死：每次运行的报告按“角色@后端”统计卡死次数，一次运行卡死 3 次以上告警；后端熔断时告警
  （`llm:<后端>`），恢复响应后自动解除。
- 运行报告新增：积压数量（连续 3 次运行增长时告警）、死信增量（一次增加超过 30 篇时告警）。
- 遇到 SQLite 写锁超时，抓取图的节点会自动重试（LangGraph `RetryPolicy`）。
- `sde-rag backup`：用 SQLite 在线备份 API 备份并压缩（82 MB 的数据库压缩后 45 MB，约 4 秒），保留 7 份。
- `sde-rag reconcile`：修复表间引用（悬空的“已见过”记录、孤立的切块、向量和全文索引行），下次运行完整列出所有 GitHub 仓库，
  重新计算热度（时间衰减），删除过期的旧索引版本，检查全文索引的完整性。在工作数据库的副本上运行：1.6 秒，没有发现不一致。
- `sde-rag watchdog-ui`：检查网页界面的 `/health`，连续 2 次失败就重启 `sde-ui.service` 并告警。
- `sde-rag install-systemd [--enable] [--ui] [--remove]`：按本机路径生成 9 个单元到 `deploy/systemd/`（不提交）并链接到
  `~/.config/systemd/user`；不会覆盖已存在的同名单元。
- 测试：新增 15 个（共 69 个），包括模型挂起后检测、切到备用模型、熔断、告警和恢复。
  在副本上做了一次真实的强制抓取：reconcile 之后完整列出了 GitHub 的 314 个文件，全部按 blob SHA 识别为没有变化，
  下载 0 次，没有错误，没有卡死，耗时 42 秒。

### 第 2 步：LLM 抽题、防编造、近似重复合并 —— 已完成（2026-10-31）

- 抽题（`extract` 节点，`extractor` 角色）：面经帖子按约 6,000 字符一段读取。模型给出帖子是否与面试有关、公司、职位、级别、
  年份，以及每道题的规范英文表述、原文引用、帖子给出的答案和面试轮次。引用和原文对不上的题（相似度低于 0.8；忽略标记、
  大小写和标点；中文逐字比较）丢弃并计数，一次运行中超过 15% 时告警。模型处理失败的段落对半拆开再试。抽题有自己的状态、
  尝试次数和死信（`sde-rag replay --stage extract`），模型不可用时帖子照样以正文形式入索引。
- 转载：对正文计算 SimHash，与已读过的帖子相差不超过 3 位的标记为 `duplicate`，不再读取。
- 近似重复的题（`dedup` 节点，`dedup_judge` 角色）：阈值在 M1 数据上实测确定（见设计文档 6.4 节）。自动合并要求相似度
  ≥ 0.95，并且实词相同、顺序基本一致；其余 ≥ 0.92 的题对交给判断模型（每次运行 600 对）。被合并的措辞留作别名，合并有记录。
- 在工作数据库的副本上实测：6,633 道题的题目文本一次性计算向量用了 5 分钟。抽题模型读一段 6,000 字符约 16 秒
  （218 篇帖子共约 1.5 到 2 小时，按每次运行 40 篇分摊）。判断模型改用扁平输出（题对编号的两个列表）后每秒约判断 3.5 对；
  对象列表的输出在 4 批里有 3 批 JSON 格式出错。一次读 8 篇帖子的运行：提出 153 道题，保留 148 道，4 道因引用对不上被丢弃
  （2.6%，都是模型改写了代码格式的“代码输出什么”类题目），新增 74 道题；自动合并 63 对，判断 100 对、合并 58 对；耗时 7 分 21 秒。
- 热度现在反映跨来源的重复：合并后，“Where do you see yourself in five years?”有 6 次出现、来自 3 个来源。
- 测试：新增 10 个（共 79 个）。

### 第 4 步：重排序、充分性判断和改写循环、评审员 —— 已完成（2026-10-31）

- `rerank`：用 `BAAI/bge-reranker-v2-m3-int8`（fastembed，CPU）给 30 个候选和问题打分，取 6 个进入上下文，同一篇帖子最多 3 段
  （第一次实测时一篇长文章占满了全部 6 个位置）。评审员判为“有错误”的来源答案扣 3 分，评审员的更正跟着它一起进入上下文。
  重排序失败时保留检索顺序。
- `grade` / `rewrite`：本地模型判断上下文是否足以回答问题；不够时加上它给出的新检索词再检索一次，最多两次。判断失败时当作“足够”。
- 评审员（`reviewer` 角色，`claude -p` 调用 Sonnet，只读，JSON schema）：队列 `review_jobs` 带优先级（1：用户点了“请评审员复核”，
  2：`solve` 类回答，4：来源答案）；每日额度按调用次数计（失败和重试也算；一批算一次），保留 40 次给交互使用；失败重试，
  连续失败 3 次告警。网页界面进程在后台线程里处理队列（失败后暂停一分钟，避免坏掉的评审员把额度用光）；页面先显示“评审中”，
  完成后显示结论、问题和更正；抓取时每次运行评审 10 个最热题目的来源答案，每批 5 个。对提问回答的评审包含用户的提问，永不公开。
- `sde-rag review --list | --run N | --sources N | --show ID`；`sde-rag query --review` 会等待评审结论。
- 在工作数据库上实测（“如何设计一个限流器（rate limiter）？”）：完成重排序，判断模型第一轮就认为上下文足够，回答带引用；
  评审结论为正确（5/5、5/5），一个小问题（B = 60 的令牌桶一分钟内最多可放行约 120 次，比“每分钟 60 次”的说法多）。
  评审员每次约 5 到 60 秒；第一次提问时还下载了重排序模型（0.57 GB）。
- 测试：新增 9 个（共 98 个）。

### 第 4b 步：复杂问题的规划器 —— 已完成（2026-10-31）

- `understand` 输出 `complexity`；一条消息里有两个以上问号时，即使路由模型判为简单也按复杂处理；路由模型失败时由规则判断。
  复杂问题进入 `plan`（`planner` 角色：本地模型开思考，gateway 作为退回模型），简单问题照旧。
- `graphs/planner.py`：计划校验（2 到 4 个子问题，每个子问题都有代码判定的标准，检索词是英文，依赖没有环；只有一个子问题表示
  “不需要规划”）；子问题作为 LangGraph `Send` 分支执行，有依赖的在后一批执行，检索词里的 `{s1}` 替换为 s1 找到的内容；
  `min_items`、`has_kind`、`mentions` 由代码判定，`covers` 用一次 grader 调用判定；换新检索词重试 1 次；`check_plan` 和 `replan`
  （已达标和没改动的子问题保留结果，什么都没改的重新规划直接结束）；时间和调用次数预算；`synthesize` 轮流从各个子问题取结果，
  按提纲回答，并说明哪些部分没有找到来源。每种失败都会退回简单路径，或用已经找到的内容回答。
- 第一次实测（“Python 的 GIL 对多线程有什么影响？Go 的 goroutine 之间又是怎么通信的？”）：拆成两个子问题，都达标，46 秒完成；
  但规划器把两个子问题都标成了 `topic`，答案变成了两串面试题列表。已修复：要答案的问题，其子问题改为 `solve`（提示词也写明了）。
  第二次实测：两个子问题都重试了，子问题 1 重新规划过，最后因为预算用完而结束；答案质量好（CPU 密集与 I/O 密集的区别、GIL 不保证
  线程安全、channel 和 select），耗时 3 分 21 秒。子问题 1 没通过 `min_items`，是因为子问题以中文写的目标为查询重排；改为以英文
  检索词重排后，同样的结果得分超过门槛（1.13 和 0.91，原来是 −0.28 和 −0.95）。延迟主要来自规划器的思考和额外的 grader 调用。
